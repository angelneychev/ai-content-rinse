# Writing conventions

Apply these rules to assistant replies, public descriptions, release notes, documentation, and interface labels. The preference concerns the whole writing style, not just replacing one dash.

- Use ordinary keyboard punctuation: hyphens, straight quotation marks, and three periods when an ellipsis is actually needed. Use ordinary spaces, with no invisible characters or decorative Unicode separators.
- Avoid decorative emoji, ornamental headings, excessive bold, stock introductions, and repetitive concluding summaries. Use lists when the content actually benefits from them.
- Write direct, natural sentences. Avoid canned marketing language, inflated claims, forced contrasts, and repetitive sentence patterns. Explain concrete behavior in the user's language.
- Before sending or publishing, first review the meaning and wording, then simplify the structure, normalize punctuation and whitespace, and read the final rendered result. Mechanical character checks support this review but do not replace it.
- Apply the same review to artwork captions, release descriptions, and text visible in screenshots. Do not leave older public assets with inconsistent interface wording when releasing updated copy.
- WordPress.org automatically converts a spaced hyphen into a typographic dash. Use colons or separate sentences in the directory name and readme prose, then verify the rendered public page.

Preserve original characters when they are deliberate cleaning examples, test fixtures, detection rules, quoted source material, or third-party license text. Never change syntax such as HTML comments to satisfy a prose convention.

These writing preferences do not by themselves authorize changes to the plugin's content-cleaning rules. Do not silently remove punctuation, emoji, or other visible characters from users' stored content merely to apply the author's writing style.
